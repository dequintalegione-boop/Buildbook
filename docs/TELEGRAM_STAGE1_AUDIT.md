# Аудит Telegram-модуля Buildbook

Дата аудита: 2026-11-26  
База проверки: `main` на коммите `ab6dc99` и связанные Telegram-ветки/PR.

## Архитектура, которую нужно сохранять

- `index.html` — основной интерфейс и Telegram-панель.
- `client/telegram-overrides.js` — отдельные обработчики интерфейса белого списка и журналов.
- `host/local-api.mjs` — loopback-only API. Браузерные запросы после bootstrap защищены HttpOnly-сессией.
- `host/buildbook-local-host.mjs` — композиция локального хоста, канонического профиля, Telegram-сервиса и локального API.
- `host/telegram-host-service.mjs` — сборка polling, update gate, inbox processor, idempotency и отправки ответов.
- `host/telegram-update-gate.mjs` — серверная проверка Telegram ID до помещения обновления в очередь; пропускаются только личные текстовые сообщения.
- `host/telegram-command-adapter.mjs`, `host/telegram-finance-command.mjs`, `host/profile-finance-adapter.mjs` — разбор команд и запись в существующий финансовый профиль Buildbook.
- `host/activity-log.mjs` — отдельный журнал безопасных операционных событий.
- `host/telegram-allowlist-meta.mjs` и `host/telegram-allowlist-handlers.mjs` — метаданные доверенных пользователей и синхронизация активных ID с .env и работающим gate.

Не создавать вторую финансовую базу для Telegram. Финансовые операции и статистика должны оставаться в каноническом профиле Buildbook.

## Уже присутствовало в main до этой ветки

1. Локальный хост с loopback bind, защищённой браузерной сессией и PWA same-origin bootstrap.
2. Telegram polling, durable inbox/offset, дедупликация обновлений, ограничение повторных экземпляров и обработка ошибок/429.
3. Проверка Telegram ID на стороне host до разбора и записи команды.
4. Мастер токена и Telegram user ID, проверка токена через Bot API, получение профиля бота; токен не возвращается интерфейсу.
5. Добавление и удаление ID в белом списке, комментарии и динамическое обновление активного gate.
6. Редактор команд меню Telegram через getMyCommands/setMyCommands.
7. Добавление расхода, дохода и запрос месячной статистики через финансовую модель Buildbook; защита от повторной доставки.
8. Запуск, остановка и перезапуск Telegram из интерфейса.
9. Управление автозапуском локального хоста и диагностика Windows Task Scheduler.
10. Последние сообщения Telegram и журнал действий локального хоста.

## Что добавлено в feature/telegram-complete-plan

- Неограниченное хранение журнала по умолчанию. Явный параметр `limit` всё ещё можно передать для тестов или специальных сценариев.
- Offset pagination для журнала и API `/api/activity?limit=...&offset=...`.
- UI-поиск, фильтр статуса, «Загрузить ещё» и экспорт всей истории в JSON.
- Модель белого списка версии 2: `id`, `comment`, `active`, `addedAt`; старый формат версии 1 читается без потери комментариев.
- Отключённые пользователи остаются в метаданных, но удаляются из списка ID в .env и из live gate.
- Нельзя сохранить пустой активный список; проверяются дубликаты и некорректные даты.
- Добавлены регрессионные тесты на хранение более 500 событий, пагинацию, active state и API-валидацию.

## Что нельзя считать завершённым без дальнейшей реализации/проверки

1. Отдельные настройки включения/выключения обработки каждой финансовой команды.
2. Измерение задержки Telegram API и явная индикация устаревшего статуса.
3. Полный установщик, который один раз выбирает и сохраняет именно папку установки приложения, а не только папку данных.
4. Реальная проверка аварийного восстановления и установки на Windows-машине пользователя.
5. Сквозная проверка всех критериев плана на установленном PWA, включая повторную доставку, отказ в доступе и сохранение профиля.
