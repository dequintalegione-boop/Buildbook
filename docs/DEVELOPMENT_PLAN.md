# План разработки Buildbook

Этот документ фиксирует подтверждённые направления разработки. Идеи, которые ещё обсуждаются, не считаются утверждёнными задачами.

## Ближайший этап: Telegram на устройстве пользователя

- Добавить отдельную вкладку «Telegram» с настройкой подключения и статистикой работы.
- Запустить Telegram-процесс как фоновый локальный сервис с автозапуском; он должен продолжать работу при закрытом окне Buildbook.
- В первой версии предоставить боту действия «Доход», «Расход» и «Статистика за месяц».
- Настроить белый список Telegram user ID. Проверять доступ на стороне сервиса до обработки обновления; посторонних пользователей игнорировать без ответа.
- Обеспечить устойчивую очередь входящих обновлений и идемпотентную обработку: повторная доставка не должна создавать повторные финансовые операции.
- Не подтверждать обработку сообщения до успешной записи операции в основное хранилище Buildbook.
- Вкладка должна показывать состояние сервиса, очередь, последние ошибки и статистику обработанных операций.

Файловый store — только серверный строительный блок, а не готовая миграция приложения. Пока браузерный интерфейс не подключён к нему, Telegram не должен создавать реальные доходы или расходы.

## Архитектурное требование: перенос на отдельный сервер

- Разделить интерфейс, бизнес-логику, транспорт Telegram и адаптер хранения данных.
- В первой версии использовать локальный хост на устройстве пользователя.
- Заложить заменяемый адаптер хоста/транспорта, чтобы позднее вынести сервис на отдельный сервер без переписывания интерфейса и бизнес-логики.
- Не создавать независимую финансовую базу Telegram, которая расходится с данными Buildbook.

## Будущие этапы

- Реализовать роли и отдельные уровни доступа с разрешениями для разных ролей.
- Реализовать синхронизацию данных между всеми клиентами Buildbook.

## Ограничение доставки Telegram

Telegram хранит неполученные обновления бота ограниченное время (до 24 часов). Локальный сервис может надёжно поставить в очередь обновления, которые он успел получить, но не может гарантировать получение сообщений после более длительного отключения, если Telegram уже удалил их. Для гарантированной приёмки при длительном простое потребуется постоянно доступный внешний приёмник/сервер. Это ограничение должно быть явно отражено в статусе сервиса и документации.

## Критерии готовности первой версии

- Локальный сервис запускается отдельно от окна приложения и восстанавливается после перезагрузки устройства.
- Белый список проверяется до выполнения любых действий.
- Входящие обновления сохраняются в устойчивую очередь, обрабатываются последовательно и не создают дубли при повторной доставке.
- Финансовые операции и статистика используют единое основное хранилище Buildbook.
- Состояние сервиса, очередь и ошибки видны во вкладке Telegram.
- Пройдены тесты очереди, повторной доставки, отказа записи, перезапуска сервиса и проверок доступа.
