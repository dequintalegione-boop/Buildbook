# План разработки Telegram-модуля Buildbook

> Статус документа: план согласован, реализация по этому плану ещё не отмечена как выполненная.
>
> Основная цель: сделать Telegram-модуль удобным для обычного пользователя — без командной строки и ручного редактирования конфигурационных файлов. Первоначальную настройку пользователь проходит через мастер, выбирает папку установки один раз, а дальнейшее управление выполняет из Buildbook.

## 1. Зафиксированные требования

1. Установка и настройка должны быть максимально автоматизированы. Пользователь не должен пользоваться командной строкой или вручную редактировать конфиги. Если Windows требует явного запуска установщика или подтверждения прав, это действие объясняется и подтверждается штатным способом.
2. Папка установки выбирается при первой настройке. Выбранный путь сохраняется и повторно не запрашивается без необходимости.
3. Первый набор Telegram-команд:
   - добавить расход;
   - добавить доход;
   - показать статистику за месяц.
4. Бот принимает и передаёт сообщения в Buildbook только от пользователей белого списка. Сообщения остальных пользователей не должны обрабатываться и не должны создавать записи.
5. Управление подключением должно иметь отдельные действия: запуск, остановка и перезапуск.
6. История событий хранится полностью: автоматическое удаление старых событий по сроку хранения по умолчанию не выполняется.

## 2. Принципы реализации

- **Без командной строки:** настройка, управление, диагностика и восстановление доступны из интерфейса.
- **Без обхода защиты Windows:** браузер не запускает BAT-файлы напрямую. Для системных действий используется явно запускаемый пользователем установщик или локальный компонент с ограниченным набором разрешённых операций.
- **Безопасность по умолчанию:** неизвестный отправитель не проходит дальше проверки белого списка.
- **Buildbook — источник финансовых данных:** бот не ведёт отдельную независимую финансовую базу.
- **Сохранность:** перезапуск и обновление не должны удалять настройки, белый список, журнал событий или финансовые записи.
- **Понятные ошибки:** пользователю показывается причина и следующий шаг, а технические подробности доступны в диагностике.
- **Работающие действия:** кнопки не должны быть заглушками; каждое действие получает реальный результат и обрабатывает ошибки.
- **Постепенное внедрение:** сначала аудит существующего кода, затем изменения небольшими проверяемыми этапами.

## 3. Целевая структура вкладки Telegram

### 3.1. Панель состояния подключения

Показывать:
- состояние локального сервера: работает, остановлен или ошибка;
- состояние Telegram-бота: подключён, отключён, запускается или требуется настройка;
- время последней успешной связи с Telegram;
- фактическую задержку ответа Telegram API и время последней проверки;
- время работы с момента последнего запуска;
- количество обработанных сообщений;
- количество отклонённых сообщений;
- последнее событие или ошибку.

Если данные устарели, это должно быть явно обозначено. Нельзя показывать успешную связь только на основании того, что процесс существует.

### 3.2. Управление подключением

Кнопки:
- **Запустить**;
- **Остановить**;
- **Перезапустить**.

Поведение:
- показывать состояние выполняемого действия и блокировать повторные нажатия;
- обновлять статус после подтверждённого результата;
- при ошибке сообщать, что не удалось сделать, и предлагать понятный следующий шаг;
- корректно обрабатывать уже запущенный или уже остановленный процесс;
- не допускать запуска нескольких экземпляров;
- при недоступности локального сервера объяснять, что именно недоступно.

### 3.3. Логи и события

Предусмотреть просмотр:
- всех событий;
- подключения и отключения;
- входящих сообщений;
- сообщений доверенных пользователей;
- отклонённых сообщений;
- передачи данных в Buildbook;
- ошибок;
- действий пользователя: изменение настроек, запуск, остановка и перезапуск.

Для события показывать дату и время, тип, краткое описание, результат и при необходимости Telegram ID или идентификатор связанной операции.

Инструменты:
- фильтрация по типу;
- поиск по тексту и ID;
- очистка фильтров;
- экспорт журнала;
- просмотр подробностей события.

Требование «все события» означает, что журнал не обрезается автоматически и не удаляется по умолчанию. Следует отдельно предусмотреть архивирование и управление размером журнала, не вводя автоматическое удаление без явного согласования.

Не записывать токен бота, секреты и полный текст финансовых сообщений без обоснованной необходимости. Для неизвестных отправителей достаточно фиксировать факт отклонения и безопасные метаданные.

### 3.4. Белый список доверенных пользователей

Таблица:
- Telegram ID — обязательный уникальный идентификатор;
- комментарий — например, имя или пояснение;
- дата добавления;
- состояние: активен или временно отключён.

Действия:
- добавить пользователя;
- изменить ID или комментарий;
- удалить пользователя с подтверждением;
- временно отключить пользователя;
- показать число активных пользователей.

Проверять корректность ID и отсутствие дубликатов. Список сохраняется после перезапуска.

**Обязательное правило обработки:** проверка Telegram ID выполняется до разбора финансовой команды и до любых изменений данных Buildbook. Если отправителя нет в активном белом списке, обработка прекращается. Сообщение не создаёт доход, расход или другую запись.

### 3.5. Настройка команд

Кнопка **«Настроить команды бота»** открывает отдельное окно настроек.

На первом этапе доступны три команды:
1. Добавить расход.
2. Добавить доход.
3. Показать статистику за месяц.

Для каждой команды предусмотреть:
- переключатель включения;
- описание;
- формат сообщения;
- пример корректного сообщения;
- обязательные и необязательные поля;
- понятные ответы при ошибке формата.

Команды, не входящие в первый согласованный набор, остаются выключенными. Включение команды не отменяет проверку белого списка.

### 3.6. Мастер первоначальной настройки

Кнопка **«Настроить Telegram»** запускает пошаговый мастер:

1. Кратко объяснить, что потребуется для подключения.
2. Предложить выбрать папку установки.
3. Проверить доступность и возможность записи в выбранную папку.
4. Создать необходимую структуру файлов.
5. Запросить токен бота через защищённое поле.
6. Проверить токен через Telegram API.
7. Получить и показать имя бота.
8. Сохранить настройки безопасным способом.
9. Проверить локальный сервер.
10. Запустить Telegram-компонент.
11. Проверить обмен с Telegram.
12. Показать итоговый экран и состояние подключения.

Мастер должен сохранять безопасный прогресс и позволять продолжить настройку после закрытия. Токен не должен отображаться полностью после сохранения.

## 4. Установка без ручной работы в командной строке

Целевой пользовательский сценарий:

1. Пользователь нажимает настройку Telegram в Buildbook.
2. Buildbook предлагает скачать установочный пакет.
3. Пользователь запускает пакет обычным способом.
4. Открывается простой мастер установки.
5. Пользователь выбирает папку установки один раз.
6. Установщик проверяет необходимые компоненты и при необходимости предлагает установить их.
7. Установщик создаёт файлы, конфигурацию и параметры автозапуска.
8. Пользователь возвращается в Buildbook.
9. Buildbook проверяет локальный сервер и завершает подключение Telegram.

В папке установки должны быть предусмотрены:
- запуск и остановка локального компонента;
- добавление и удаление автозапуска;
- конфигурация;
- код Telegram-компонента;
- пользовательская инструкция;
- папки данных и журналов;
- средства диагностики и восстановления.

### Ограничение браузера и Windows

Веб-страница не может безопасно запускать произвольные BAT-файлы или программы на компьютере пользователя. Поэтому интерфейс не должен пытаться обходить ограничения браузера. Системные действия выполняются явно запущенным установщиком либо локальным компонентом с ограниченным набором разрешённых операций. Запросы Windows на подтверждение прав не скрываются.

## 5. Обработка Telegram-сообщений

### 5.1. Общий поток

1. Получить обновление от Telegram.
2. Извлечь Telegram ID отправителя.
3. Проверить активный белый список.
4. Если отправитель не разрешён — прекратить обработку.
5. Проверить, включена ли команда.
6. Проверить формат сообщения и обязательные поля.
7. Передать данные в существующую финансовую логику Buildbook.
8. Убедиться, что запись успешно сохранена.
9. Отправить подтверждение пользователю.

Проверка доступа должна быть серверной/локальной частью обработки, а не только ограничением видимых кнопок в интерфейсе.

### 5.2. Добавление расхода

Согласовать и реализовать формат сообщения с обязательными полями, суммой, датой, категорией и необязательным комментарием — в соответствии с возможностями существующей формы расходов Buildbook.

Проверить:
- допустимость суммы и даты;
- доступность категории;
- обработку отсутствующих полей;
- понятный запрос уточнения при неполных данных;
- подтверждение только после успешного сохранения;
- защиту от повторного создания операции при повторной доставке одного сообщения.

### 5.3. Добавление дохода

Использовать существующую финансовую модель Buildbook. Реализовать проверку обязательных полей, суммы, даты, источника/категории и комментария, если они поддерживаются текущей моделью.

При ошибке не создавать неполную запись. Подтверждать сохранение только после успешной записи в Buildbook. Защититься от дублей при повторной доставке сообщения.

### 5.4. Статистика за месяц

Статистика запрашивается из Buildbook, а не из отдельной базы Telegram-компонента.

На первом этапе показывать:
- доходы за текущий календарный месяц;
- расходы за текущий календарный месяц;
- разницу доходов и расходов.

Следует использовать те же правила расчёта, что и соответствующий отчёт Buildbook. Возможность запрашивать произвольный период оставить для следующего этапа.

## 6. Архитектура и данные

Разделить обязанности:
- **Интерфейс Buildbook:** настройка, состояние, команды, белый список и журнал.
- **Локальный сервер:** безопасный обмен между интерфейсом и Telegram-компонентом.
- **Telegram-компонент:** соединение с Telegram и получение сообщений.
- **Buildbook:** источник истины для финансовых записей и расчётов.

Токен хранить отдельно от обычных логов и интерфейсных данных. Не показывать его полностью после сохранения. Предусмотреть смену токена и обработку отозванного или недействительного токена.

Настройки, белый список и состояние команд должны сохраняться после перезапуска. Обновление Telegram-компонента не должно удалять пользовательские данные. Финансовые записи остаются самостоятельными и не зависят от срока хранения журнала событий.

До реализации нужно проверить текущие механизмы локального host, Telegram polling, хранения настроек и финансовых операций. Не создавать параллельную финансовую модель, если подходящая уже есть.

## 7. Этапы реализации

### Этап 1. Аудит существующей реализации

- Проверить текущую Telegram-вкладку и связанные компоненты.
- Найти маршруты и API локального сервера.
- Проверить сохранение настроек и белого списка.
- Проверить запуск, остановку и восстановление Telegram-компонента.
- Проверить обработку входящих сообщений и интеграцию с финансами.
- Проверить существующие тесты и документацию.
- Составить список повторно используемого кода, дефектов и недостающих функций.

**Результат:** техническая карта текущего состояния и конкретный список изменений.

### Этап 2. Новая структура вкладки

- Переработать компоновку Telegram-вкладки.
- Добавить панель состояния и управления.
- Добавить журнал событий с фильтрами и поиском.
- Добавить таблицу белого списка и формы добавления/редактирования.
- Добавить отдельное окно команд.
- Добавить запуск мастера настройки.

**Результат:** интерфейс подключён к реальным действиям, без кнопок-заглушек.

### Этап 3. Управление локальным компонентом

- Реализовать запуск, остановку и перезапуск.
- Обрабатывать повторные нажатия и уже запущенный процесс.
- Обновлять статус по фактическому состоянию.
- Показывать понятные ошибки.
- Исключить запуск нескольких экземпляров.
- Проверить аварийное завершение и восстановление.

**Результат:** пользователь управляет компонентом из Buildbook.

### Этап 4. Установка и мастер настройки

- Подготовить установочный пакет.
- Реализовать выбор папки при первой настройке и сохранение пути.
- Создать структуру файлов и безопасное хранение конфигурации.
- Проверять и при необходимости устанавливать нужные компоненты.
- Реализовать ввод и проверку токена через Telegram API.
- Добавить проверку локального сервера и итоговый экран.
- Реализовать продолжение прерванной настройки.

**Результат:** пользователь устанавливает и подключает Telegram без командной строки и ручного редактирования конфигов.

### Этап 5. Белый список

- Реализовать добавление, изменение, отключение и удаление пользователей.
- Добавить валидацию и защиту от дубликатов.
- Обеспечить сохранение списка.
- Встроить проверку отправителя в начало обработки.
- Проверить, что неизвестный отправитель не может создать финансовую запись.

**Результат:** обрабатываются только сообщения активных доверенных пользователей.

### Этап 6. Команды и финансовая интеграция

- Реализовать экран включения/выключения команд.
- Оставить команды выключенными по умолчанию, если пользователь ещё не включил их.
- Реализовать добавление расхода.
- Реализовать добавление дохода.
- Реализовать статистику за текущий месяц.
- Подключить команды к существующей финансовой логике Buildbook.
- Добавить валидацию, обработку неполных сообщений и защиту от дублей.
- Реализовать подтверждения и сообщения об ошибках.

**Результат:** три согласованные команды работают от Telegram-сообщения до данных Buildbook.

### Этап 7. Журнал и диагностика

- Записывать события подключения, обработки сообщений, передачи данных и ошибок.
- Записывать важные действия пользователя.
- Добавить фильтры, поиск, подробности и экспорт.
- Исключить попадание токенов и секретов в журнал.
- Сохранить полную историю без автоматического удаления.

**Результат:** причины проблем доступны из интерфейса без консоли.

### Этап 8. Автозапуск и восстановление

- Реализовать управление автозапуском через интерфейс.
- Проверять состояние после аварийного завершения.
- Реализовать безопасное восстановление.
- Не допускать нескольких экземпляров.
- Показывать результат восстановления и ошибки.

**Результат:** после перезагрузки Windows или сбоя компонент возвращается в рабочее состояние, если это возможно.

### Этап 9. Тестирование и стабилизация

Проверить:
- чистую установку и повторный запуск;
- перезагрузку Windows;
- неверный, отозванный и отсутствующий токен;
- отсутствие интернета и недоступность Telegram;
- остановленный или аварийно завершившийся локальный сервер;
- повторную доставку одного сообщения;
- сообщение от пользователя вне белого списка;
- выключенную команду;
- неправильный формат суммы или даты;
- ошибку сохранения в Buildbook;
- отсутствующую или повреждённую конфигурацию;
- обновление компонента без потери настроек;
- восстановление после аварийного завершения.

**Результат:** проверенные сценарии установки, ежедневного использования и восстановления.

## 8. Дальнейшие улучшения

Эти возможности не входят в первый рабочий релиз, но должны учитываться при проектировании.

### Расширение команд
- статистика за произвольный период;
- просмотр последних операций;
- редактирование и удаление операций;
- баланс и поиск по категориям;
- напоминания и регулярные операции;
- команды для объектов и других разделов Buildbook после отдельного согласования.

### Улучшение ввода
- пошаговый диалог при нехватке данных;
- подсказки формата сообщения;
- подтверждение перед сохранением неоднозначных операций;
- голосовые сообщения с распознаванием речи после отдельной оценки приватности и стоимости;
- фото чека с распознаванием и обязательным подтверждением данных пользователем.

### Управление доступом
- удобное добавление пользователя по Telegram ID;
- временная блокировка доверенного пользователя;
- журнал изменений белого списка;
- разные права для добавления операций и просмотра статистики.

### Надёжность и обслуживание
- резервная копия конфигурации;
- проверка целостности настроек;
- безопасное обновление Telegram-компонента;
- откат на предыдущую версию при неудачном обновлении;
- диагностический отчёт для поддержки;
- настройка архивирования журнала.

### Удобство интерфейса
- индикатор незавершённой настройки;
- мастер повторного подключения;
- предупреждение о недействительном токене;
- отображение версии компонента;
- кнопка проверки связи;
- открытие папки установки из интерфейса;
- переустановка компонента без удаления финансовых данных.

## 9. Критерии готовности

Telegram-модуль считается готовым, когда пользователь может:

1. Открыть вкладку и увидеть фактическое состояние подключения.
2. Запустить, остановить и перезапустить компонент из интерфейса.
3. Пройти первоначальную настройку без командной строки и ручного редактирования конфигов.
4. Выбрать папку один раз и использовать сохранённый путь в дальнейшем.
5. Добавлять, изменять, отключать и удалять доверенных пользователей.
6. Включать и выключать доступные команды.
7. Создавать расход и доход сообщением от пользователя белого списка.
8. Получать месячную статистику из Buildbook.
9. Не создавать финансовую запись сообщением от пользователя вне белого списка.
10. Просматривать и искать события, чтобы понять причину сбоя.
11. Сохранять настройки после перезапуска.
12. Восстанавливать работу после типичных ошибок без командной строки.

## 10. Рабочий порядок

Работы выполняются по этапам. Перед изменениями проводится аудит текущей реализации. После каждого этапа запускаются соответствующие проверки, исправляются найденные ошибки и фиксируется результат. Нельзя считать этап завершённым только по наличию интерфейса: проверяется полный рабочий сценарий.

При изменении существующей логики предпочтительно переиспользовать текущие API и модели данных. Новые зависимости и изменения архитектуры должны быть обоснованы аудитом. Отдельно проверять исходный интерфейс и автономную сборку Buildbook, если изменённые файлы входят в её состав.
