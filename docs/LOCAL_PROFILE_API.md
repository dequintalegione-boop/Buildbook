# Локальный профильный API

Модуль `host/local-api.mjs` предоставляет минимальный HTTP API поверх `createProfileStore`. `host/local-api-host.mjs` собирает файловое хранилище и API в управляемый локальный хост с `start()`/`stop()`.

## Запуск локального API

После задания переменных окружения запустите процесс командой:

```sh
node host/run-local-api.mjs
```

Процесс пишет в консоль адрес и порт, но не выводит токен. Он корректно закрывает сервер при `SIGINT` или `SIGTERM` (например, при Ctrl+C или остановке службы).


Хост создаётся через `createLocalApiHost({ env })`. При старте он получает эксклюзивную блокировку файла профиля; при неудачном старте блокировка освобождается, при остановке — после закрытия сервера. Обязательные переменные окружения:

- `BUILDBOOK_PROFILE_PATH` — абсолютный путь к файлу канонического профиля.
- `BUILDBOOK_LOCAL_API_TOKEN` — отдельный секрет API длиной не менее 32 байт.

Необязательные:

- `BUILDBOOK_PROFILE_LOCK_PATH` — абсолютный путь к эксклюзивной блокировке владельца канонического профиля; по умолчанию `<BUILDBOOK_PROFILE_PATH>.api-lock`. Второй API-хост с тем же профилем не запустится, пока блокировка удерживается. После аварии stale-lock намеренно требует ручной проверки и очистки.
- `BUILDBOOK_LOCAL_API_HOST` — по умолчанию `127.0.0.1`; разрешены только loopback-адреса.
- `BUILDBOOK_LOCAL_API_PORT` — по умолчанию `43127`; значение `0` выбирает свободный порт (для тестов).

Токен задаётся только в окружении локального процесса и не передаётся браузерному коду. Модуль предоставляет lifecycle API, но пока не является установщиком системной службы и не обеспечивает автозапуск после перезагрузки.

## Совместный запуск с Telegram

Для общей канонической записи профиля используйте совместный хост:

```sh
node host/run-buildbook-local-host.mjs
```

Он создаёт один экземпляр профильного хранилища и передаёт его и локальному API, и Telegram-host. Не запускайте рядом отдельный Telegram-процесс с другим файлом профиля: это создаст независимый реестр. Совместный запуск требует переменных локального API и Telegram из документации интеграции; все пути данных должны быть абсолютными и не пересекаться.

## Маршруты

- `GET /api/health` — проверка доступности процесса.
- `GET /api/telegram/status` — только авторизованный, ограниченный статус Telegram без токена, текста сообщений и произвольных ошибок. Для обычного API-хоста без Telegram endpoint возвращает 404.
- `GET /api/profile` — возвращает `{ revision, profile }`; до первого сохранения профиль равен `null`.
- `PUT /api/profile` — принимает `{ expectedRevision, profile }` и возвращает новую ревизию. Устаревшая ревизия даёт HTTP 409 и код `BUILD_BOOK_STORAGE_CONFLICT`.
- `POST /api/profile/import` — принимает `{ expectedRevision, envelope }` из файла переноса. Сервер независимо проверяет точный набор полей, ISO-8601 дату с проверкой календарных компонентов, версию схемы, SHA-256 и размер сериализованного payload (до 32 MiB). Импорт разрешён только в пустой профиль; непустой целевой профиль возвращает 409 `BUILD_BOOK_IMPORT_TARGET_NOT_EMPTY`. Секреты и неизвестные поля не принимаются.

API принимает JSON до 34 MiB: лимит покрывает профиль до 32 MiB и JSON-конверт. Импорт дополнительно ограничивает сериализованный payload 32 MiB. Успешные и ошибочные ответы используют `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Cross-Origin-Resource-Policy: same-origin`, `Cross-Origin-Opener-Policy: same-origin` и ограничительную `Permissions-Policy`. Ошибки формата возвращаются как 400, неподдерживаемый тип содержимого — 415. Каждый запрос требует `Authorization: Bearer <accessToken>`; токен должен быть не короче 32 байт. Сравнение токена выполняется constant-time. Запросы с посторонним `Origin` или `Host` отклоняются. CORS preflight разрешает `POST` для импорта вместе с `GET`/`PUT`; это не отменяет bearer-аутентификацию самого запроса. Сервис разрешено привязывать только к loopback-интерфейсу, не к LAN или публичному адресу.

## Клиентский транспортный модуль

`host/local-profile-client.mjs` — браузерный транспортный клиент для health/read/write/import. Он принимает API-токен только через аргумент создания клиента, не сохраняет его и не помещает в URL. Перед созданием клиента адрес проверяется: допускаются только HTTP и loopback-хосты `localhost`, `127.0.0.1` или `::1`; внешние хосты, credentials в URL, путь, query и fragment отклоняются до первого запроса. Для запросов с bearer-токеном отключены редиректы, ambient credentials, кеширование и referrer. Это предотвращает случайную отправку bearer-токена на произвольный адрес через `baseUrl`, но не защищает от вредоносного ПО с правами того же пользователя. Ошибки сети получают код `BUILD_BOOK_LOCAL_API_UNAVAILABLE`, а конфликт ревизии сохраняет HTTP 409 и код `BUILD_BOOK_STORAGE_CONFLICT`. Тайм-аут ожидания ответа по умолчанию — 30 секунд; его можно задать параметром `requestTimeoutMs` в диапазоне 1–120000 мс. По истечении срока запрос прерывается через `AbortController`, клиент возвращает `BUILD_BOOK_LOCAL_API_TIMEOUT`. Метод `importProfile(envelope, expectedRevision)` отправляет файл переноса в `POST /api/profile/import`, ограничивает тело запроса 34 MiB и проверяет ответ `{ imported: true, revision }`. Он не создаёт резервную копию и не переключает IndexedDB; вызывающая сторона должна заранее показать предпросмотр, подтвердить действие и проверить результат чтением профиля.

Пример использования из доверенного bootstrap-кода:

```js
import { createLocalProfileClient } from './host/local-profile-client.mjs';

const client = createLocalProfileClient({ accessToken: tokenFromSecureBootstrap });
const { profile, revision } = await client.readProfile();
const nextRevision = await client.writeProfile(profile, revision);
```

Этот модуль не является безопасным bootstrap токена и пока не выбран стартовым репозиторием интерфейса. Bootstrap выполняется отдельным действием во вкладке Telegram; runtime подключается только к уже установленной HttpOnly-сессии. Не передавайте токен из URL, общего профиля, репозитория приложения или Telegram-бота. Запросы из `file://` остаются неподдержанными, так как opaque Origin `null` не допускается.

## Подключение обычного UI

Обычный `index.html` динамически загружает `client/canonical-profile-runtime.mjs` только при явно выбранном режиме `canonical`. Режим устанавливается после успешного импорта профиля в пустую цель, повторного чтения и совпадения SHA-256, затем пользователь отдельно подтверждает перезапуск на файловом профиле. На старте runtime проверяет действующую HttpOnly-сессию через `GET /api/profile`, проверяет наличие профиля и только затем подменяет repository приложения. Ошибка сети, 401 или пустая цель блокирует запуск; автоматического перехода к IndexedDB нет. Потеря сессии или ошибка записи во время работы также блокирует дальнейшее редактирование; если профиль уже был открыт, пользователь может скачать ZIP-копию текущего состояния из экрана блокировки. Закрытие HttpOnly-сессии запрещено, пока активен канонический режим. Пользователь может явно вернуться к независимой IndexedDB из экрана ошибки или вкладки Telegram. `Buildbook-standalone.html` и браузерный тестовый режим продолжают использовать IndexedDB.

## Адаптер контракта существующего репозитория

Файловое хранилище читает профиль через уже открытый и сверенный файловый дескриптор, ограничивает чтение по размеру порциями и отвергает замену файла между проверкой пути и открытием.

`host/profile-repository-adapter.mjs` преобразует формат API-профиля в контракт `repository.readProfile()` / `repository.writeProfile(state, logs, photos, expectedRevision)`. Он сохраняет поля state/logs/photos и кодирует ArrayBuffer/TypedArray фотографии в base64-маркеры для JSON-транспорта, восстанавливая их при чтении. Обычные объекты, совпадающие по форме с бинарным маркером, экранируются как пары ключ-значение; декодирование сохраняет собственные ключи `__proto__` без изменения прототипа. Бинарные дескрипторы проверяются на канонический base64, а экранированные объекты — на повторяющиеся ключи.\n\n`client/canonical-profile-runtime.mjs` предоставляет браузерную сборку этого адаптера поверх уже созданной HttpOnly-сессии: `createCanonicalProfileRuntime({ baseUrl })` возвращает `repository`, `client` и `verifySession()`. Модуль не принимает bearer-токен, использует только `credentials: include`, ограничивает адрес loopback, отключает redirect/cache/referrer и сохраняет ошибки 401/409 как явные состояния. В нём нет IndexedDB fallback: если сессия истекла или API недоступен, чтение/запись завершается ошибкой. Модуль является подготовленным runtime-слоем; текущий `index.html` ещё не выбирает его при запуске.

Пример сборки слоёв:

```js
import { createLocalProfileClient } from './local-profile-client.mjs';
import { createProfileRepositoryAdapter } from './profile-repository-adapter.mjs';

const client = createLocalProfileClient({ accessToken: tokenFromSecureBootstrap });
const repository = createProfileRepositoryAdapter(client);
```

Адаптер не переключает приложение автоматически и не переносит существующую IndexedDB. При внедрении потребуется отдельный проверяемый процесс импорта и восстановления, а также учёт лимита тела API 8 MiB (base64 увеличивает объём фото примерно на треть). Пока что IndexedDB остаётся активным хранилищем приложения.

## Граница безопасности

Это локальный транспортный слой с обязательным секретом доступа, но пока без безопасной выдачи и ротации токена. Токен API и токен Telegram-бота — разные секреты: токен бота никогда не должен попадать в этот API или клиентский код. Защита от вредоносного процесса под тем же пользователем и безопасный bootstrap токена остаются отдельными задачами.

API пока не подключён к существующему IndexedDB-репозиторию. До реализации миграции и восстановления профиля не использовать его как единственный источник данных.


## Дополнительная защита браузерного API

Ответы API также запрещают открытие контекста через другие browsing contexts и отключают ненужные для приложения разрешения камеры, микрофона и геолокации. Проверки Host и Origin выполняются до bearer-аутентификации; opaque Origin `null` (в частности, типичный контекст `file://`) не считается доверенным. Это намеренно: запуск интерфейса напрямую из файла не является поддерживаемым способом подключения к каноническому профилю. Токен нельзя встраивать в HTML или выдавать через endpoint статуса; безопасная процедура привязки UI всё ещё должна быть реализована отдельно.


## Проверка файла переноса в браузере

`client/profile-import.js` предоставляет `BuildbookProfileImport.parseAndValidate(text)` и `validateEnvelope(envelope)`. Эти функции проверяют формат/версию, схему профиля, допустимые поля, JSON-структуру, лимит 32 MiB и SHA-256 до того, как данные будут переданы локальному API. Дополнительные поля конверта и payload отклоняются, а не игнорируются. Проверка не выполняет импорт, не записывает данные и не переключает приложение с IndexedDB. Модуль пока не подключён к UI; это только подготовительный валидатор для будущего окна предпросмотра/подтверждения.

`tests/profile-import.test.mjs` содержит проверки валидного конверта, повреждённой суммы, неподдерживаемой схемы, неожиданных полей и превышения размера. Тесты в рамках текущего изменения не запускались.


## UI предпросмотра файла переноса

В разделе настроек «Резервная копия» добавлен выбор файла «Проверить файл переноса». Интерфейс ограничивает размер исходного файла 34 MiB до чтения, затем вызывает `BuildbookProfileImport.parseAndValidate` и показывает версию схемы, размер payload и дату экспорта. При несовпадении SHA-256, неподдерживаемой версии или неожиданных полях файл отклоняется. Эта операция не вызывает API, не пишет в IndexedDB или файл хоста и не меняет активное хранилище.

Предпросмотр — отдельный шаг до будущего импорта. Подтверждение, отправка в `POST /api/profile/import`, проверка результата чтением обратно и безопасное переключение режима хранения не реализованы.
