# Локальный профильный API

Локальный host обслуживает интерфейс Buildbook и API с одного loopback-origin. Файловый профиль открыт только процессу host; браузер работает с ним через **client/canonical-profile-runtime.mjs**. В режиме **canonical** IndexedDB не используется как резервный автоматический источник данных.

## Запуск

Создайте **.env** на основе **.env.example**, задайте абсолютный путь **BUILDBOOK_PROFILE_PATH** и отдельный секрет **BUILDBOOK_LOCAL_API_TOKEN** длиной не менее 32 байт. Запустите совместный host (API + Telegram):

```sh
node host/run-buildbook-local-host.mjs
```

Для API без Telegram предусмотрен **node host/run-local-api.mjs**. Host привязывается только к loopback-интерфейсу. Не публикуйте **.env**, каталог **data/**, профиль, токены и журналы.

Открывайте Buildbook по адресу, который сообщил host, например **http://127.0.0.1:43127/**. После миграции используйте тот же hostname и порт: **localhost** и **127.0.0.1** — разные browser-origin, с отдельными настройками и cookie.

## Браузерная сессия

**BUILDBOOK_LOCAL_API_TOKEN** — секрет первоначального подключения. Он не встраивается в HTML и не сохраняется приложением. Во вкладке Telegram или на экране блокировки нажмите «Подключить» / «Повторно подключить хост» и введите этот ключ. Браузер отправляет его только на **POST /api/session/bootstrap** для обмена на HttpOnly-сессию.

- Срок сессии на сервере — 12 часов.
- Cookie **buildbook_local_session** имеет флаги **HttpOnly**, **SameSite=Strict**, **Path=/api** и **Max-Age**, согласованный с серверным сроком.
- Секрет cookie недоступен JavaScript и не записывается на диск.
- Повторный bootstrap в том же браузере отзывает предыдущую сессию и выдаёт новую.
- После истечения срока сервер удаляет сессию и возвращает HTTP 401. Для восстановления снова выполните bootstrap с ключом API.
- **POST /api/session/close** отзывает текущую сессию и удаляет cookie. В активном режиме **canonical** UI запрещает закрывать её, пока приложение использует файловый профиль.

Все API-запросы из браузера используют **credentials: include**; обычные запросы профиля не передают Bearer-токен. Bootstrap требует точный локальный Origin и JSON. API проверяет Host/Origin, ограничивает запросы loopback, использует **Cache-Control: no-store** и защитные HTTP-заголовки.

## Маршруты

- **GET /api/health** — доступность API; требует действующую сессию.
- **POST /api/session/bootstrap** — обмен Bearer-ключа на HttpOnly-сессию.
- **POST /api/session/close** — отзыв текущей браузерной сессии.
- **GET /api/telegram/status** — безопасный снимок статуса Telegram без токенов и содержимого сообщений.
- **GET /api/profile** — **{ revision, profile }**; до первой записи **profile** равен **null**.
- **PUT /api/profile** — запись **{ expectedRevision, profile }**; устаревшая ревизия возвращает HTTP 409 **BUILD_BOOK_STORAGE_CONFLICT**.
- **POST /api/profile/import** — перенос envelope только в пустой профиль; проверяет схему, SHA-256 и размер payload (до 32 MiB), затем перечитывает профиль и сверяет ревизию и SHA-256 записанных данных перед подтверждением успеха.

JSON-запрос ограничен 34 MiB. Для импортируемого payload отдельно действует лимит 32 MiB. Импорт в непустой профиль запрещён. Ответ `verified: true` выдаётся только после успешного контрольного чтения. Если проверка чтением не совпала, API возвращает `BUILD_BOOK_IMPORT_READBACK_FAILED`; запись могла уже состояться, поэтому не повторяйте импорт вслепую — сначала перечитайте профиль и сохраните резервную копию. API не принимает произвольные поля и не раскрывает секреты в статусе.

## Канонический режим UI и восстановление

Обычный **index.html** переключается в **canonical** только после явного подтверждения пользователя и успешной миграции IndexedDB в пустой файловый профиль: интерфейс проверяет envelope, делает read-back и сравнивает SHA-256. До этого обычным хранилищем остаётся IndexedDB. **Buildbook-standalone.html** и тестовый режим продолжают использовать IndexedDB.

При запуске канонического режима UI проверяет сессию чтением **GET /api/profile**, затем загружает профиль. Если сессия истекла, host недоступен или возник конфликт ревизии, приложение блокирует редактирование и не переключается автоматически на IndexedDB.

Если сессия истекла во время работы:

1. На экране блокировки скачайте ZIP-копию текущего состояния вкладки. Она нужна, чтобы сохранить возможные изменения, которые ещё не успели попасть в файл профиля.
2. Нажмите «Повторно подключить хост» и введите **BUILDBOOK_LOCAL_API_TOKEN**. Для канонического режима адрес подключения должен совпадать с текущим **location.origin**.
3. UI проверит новую сессию чтением канонического профиля, но не продолжит редактирование поверх старого состояния.
4. После сохранения резервной копии нажмите «Загрузить актуальный профиль». Приложение перезагрузится и прочитает последнюю версию с диска. Несохранённые изменения старой вкладки автоматически не объединяются и не перезаписывают профиль.

Если ошибка возникла до загрузки профиля при старте, повторное подключение и перезагрузка просто позволяют заново прочитать файл: данных в памяти приложения ещё нет. При конфликте ревизий действует тот же принцип — сначала резервная копия, затем перезагрузка с актуальным профилем.

## Telegram inbox и восстановление после сбоя

Совместный host сохраняет разрешённые Telegram updates в отдельный durable inbox до продвижения offset в Telegram. При записи host сначала синхронизирует временный файл, затем атомарно заменяет inbox; на POSIX после замены синхронизируется каталог. Это уменьшает риск потери уже подтверждённого update при аварийном завершении или отключении питания. Это не заменяет резервное копирование и не гарантирует сохранность на файловых системах или устройствах, которые не соблюдают запросы синхронизации.

После перезапуска host переводит элементы, оставшиеся в статусе **processing**, обратно в **pending** и повторяет обработку. Если сбой произошёл после создания финансовой операции, но до отметки inbox как **completed**, операция может быть передана адаптеру повторно. Поэтому адаптер канонического профиля обязан применять **idempotencyKey** как уникальный ключ в той же транзакции, что и финансовое изменение; один inbox сам по себе не обеспечивает exactly-once.

Завершённые и отклонённые элементы сохраняют ключ дедупликации, но очищают исходное содержимое Telegram update. Повторно полученный update с тем же bot ID и update ID не создаёт вторую запись. Если inbox повреждён или не читается, host должен остановить обработку и сообщить об ошибке, а не создавать пустую очередь поверх существующего файла.

Polling не получает новые updates, пока host выключен. Telegram хранит необработанные updates ограниченное время; при длительном простое они могут быть недоступны после запуска. Для приёма сообщений без перерыва нужен постоянно работающий receiver.

## Хранилище и ограничения

**host/profile-store.mjs** управляет файловым профилем и его ревизией. **host/profile-repository-adapter.mjs** адаптирует контракт **repository.readProfile()** / **repository.writeProfile(...)**, включая бинарные фотографии. **client/canonical-profile-runtime.mjs** использует только cookie-сессию, ограничивает адрес HTTP loopback и не содержит IndexedDB fallback.

Совместный **host/run-buildbook-local-host.mjs** создаёт один экземпляр файлового хранилища для API и Telegram. Не запускайте параллельно независимый Telegram-процесс с другим путём профиля. Telegram polling по умолчанию выключен (**BUILDBOOK_TELEGRAM_ENABLED=false**); включайте его только после проверки, что UI и Telegram работают с одним каноническим профилем.

Запись профиля выполняется через уникальный временный файл: host полностью записывает и синхронизирует его, затем атомарно заменяет канонический файл. На POSIX после переименования также синхронизируется каталог. Если процесс завершился до переименования, следующий запуск продолжит читать прежний канонический профиль; оставшийся временный файл не считается подтверждённой записью и автоматически не применяется. Не переименовывайте временные файлы в профиль вручную.

Host использует отдельную блокировку экземпляра, чтобы два процесса не записывали один профиль одновременно. После аварийного завершения блокировка может остаться на диске. Она намеренно не удаляется автоматически: сначала убедитесь, что Buildbook Local Host остановлен и процесс-владелец из **owner.json** больше не работает, затем удалите только каталог блокировки, указанный в **BUILDBOOK_PROFILE_LOCK_PATH** (по умолчанию рядом с профилем, суффикс **.api-lock**). Не удаляйте блокировку работающего процесса и не запускайте второй host поверх неё.

Профиль и резервные копии не шифруются автоматически. Защита от вредоносных процессов с правами текущего пользователя, безопасное хранение **.env** и резервное копирование устройства остаются ответственностью владельца локальной машины.

## Проверки

Основные регрессионные наборы:

```sh
node --test tests/profile-store.test.mjs tests/instance-lock.test.mjs tests/local-api.test.mjs tests/canonical-profile-runtime.test.mjs tests/storage-mode-wiring.test.mjs
```

Регрессионный тест проверяет, что API не сообщает об успешном импорте, если контрольное чтение не совпало. Тесты в рамках текущего этапа добавлены, но не запускались.
